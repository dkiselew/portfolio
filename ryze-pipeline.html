Each article is its own Temporal workflow with workflowId = article-{id}. Each step is an activity on its own task queue with its own limits. Temporal keeps the progress, and the activities are written so that retrying a step costs nothing extra and never creates a duplicate.

Service diagram

Workflow workers (queue article) only orchestrate and never call external services. All heavy work and external I/O runs in activity workers, and each pool scales on its own.

Stack

ComponentWhy
TemporalDurable execution: workflow history, retries with backoff, timeouts, heartbeats, task queue rate limits, a UI for debugging failed articles
Node.js + @temporalio/* (TypeScript)Workflow and activity workers. Every step is I/O-bound, so one pod handles hundreds of concurrent activities
Kubernetes + KEDAA separate deployment per queue, autoscaled on task queue backlog (a Temporal metric)
PostgresArticles: the Intake API creates the row, and workers update the status and platform-side state (image_job_id, media_id, post_url). Customers: their single site, platform and credentials. Also the per-customer token bucket: the task queue limit is shared across a platform, while each customer site has its own limit. At ~10 requests/s to platforms this is one UPDATE on the customer row, so no separate Redis is needed
S3 / MinIOPaid-for artifacts: text and images. The key is derived from article_id
Prometheus + Grafana, OpenTelemetryTemporal SDK metrics (schedule-to-start latency, backlog), cost per step, 429 rate per platform
